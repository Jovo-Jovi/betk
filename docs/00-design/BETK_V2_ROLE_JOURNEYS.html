Prep SLA

Deadline = confirmed_at + MAX(prep_days) across that seller order's items — max, not sum, because a seller prepares in parallel.

ElapsedAction
On releaseNotify: order reference, item count, ready-by date
50%Reminder
80%, not readyUrgent reminder
breachAuto-escalation → admin queue, and the buyer is told about the delay

On an order, the seller sees

  • Order reference
  • Items and quantities
  • Prep deadline

Never sees

  • Buyer name, phone or address
  • The buyer's other seller orders
  • Any part of the payment picture

May not

  • Cancel an order — escalation is the only exit
  • Sell outside the approved 3 categories
  • Publish food without food approval
  • Quote outside the tolerance band
Custom items are exempt from the 3-day cap. Their prep time comes from the accepted quote, so a two-week commission stays possible.
5.5

Admin operations

Seller approval → Payment verification → Courier handoff → Escalations → Returns → Payouts. Admin is the only role that sees both addresses, the commission and the full payment picture.

1 · Seller approvals

  • Identity, categories, agreement
  • Food verification review

2 · Payment verification

  • Proof opened via signed URL
  • One action confirms every deposit row under that master order
  • Reject → cancel, restore stock, refund, notify

3 · Ready-for-pickup queue

  • Seller orders awaiting collection
  • Handoff to courier — API or manual

4 · Escalations

  • Seller-reported and SLA breaches land in the same queue
  • Cancel + refund · reinstate with a new deadline · cancel + strike

5 · Returns & disputes

  • Evidence review, final decision
  • Refund — full, or partial per seller order

6 · Payouts & configuration

  • Derived balances, manual settlement
  • Price band · commission · tolerance · windows · prep cap · courier matrix

Stock rule on escalation resolution

Escalation reasonStock action
Out of stockSet to zero — the seller has just said the item does not exist; restoring would re-list a phantom that sells again within the hour
Any other reasonRestore normally
No automatic strikes. An SLA breach feeds the performance record; a human judges. Automatic penalties on a system-detected signal will misfire.

Handoffs

The five handoffs that carry the risk

Each is a moment where the order changes hands and could stall. Every one has a named mitigation in this model.

#HandoffFailure modeMitigation
1Buyer → Admin
payment proof		Buyer never pays; stock sits heldPayment window, auto-cancel, stock and cart restored
2Admin → Seller
release		Seller ignores an order they never agreed toPrep SLA ladder, then auto-escalation
3Seller → Courier
ready		Marked ready, never collectedAdmin ready-for-pickup queue
4Courier → BETK
COD remittance		Collected from the buyer but not remittedAdmin confirms the balance row before closure
5Any → CancellationMoney held against no orderRefund is launch-blocking, not a fast-follow
Handoff 2 is new. Removing seller acceptance created it — a seller is now bound to an order they never agreed to. The SLA ladder exists specifically to close that gap, and escalation is the seller's only exit.
