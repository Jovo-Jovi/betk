## Open issues / blockers
- One assumption to confirm with product: OD-4 resolution = OAuth additive + phone nullable + phone-gated-to-transactions (vs forcing phone OTP during OAuth signup). Default applied as above.
- **T05 finding — stock-decrement trigger missing from source:** BETK_ERD §7 / Phase-01 DoD list 5 triggers, but `BETK_DATABASE_SCHEMA.sql` defines only 4 (search_vector, review edit_deadline, dispute SLA, rating recompute). The `decrement_stock_on_confirm` trigger (R-L05/06) was NOT invented (FROM-FILE-ONLY). DB owner to add it to the source + a new migration if required.
- **T05 finding — grants not in source:** `0013_grants.sql` is standard Supabase role-grant boilerplate (step 057), the only non-verbatim file. Also: `betk`/`betk_analytics` must be added to `supabase/config.toml [api].schemas` before the Data API can reach them.
- **T05 finding — security advisors (hardening, for security gate):** ~21 tables are RLS-enabled-no-policy (default-deny, parent-scoped — remaining policies arrive in T08/later phases per C3 §5); `function_search_path_mutable` on the 6 functions; `extension_in_public` for pg_trgm/unaccent. All match the verbatim source; address during the 90-review-security gate.
- **T08 finding — orders/seller_profiles INSERT default-denied:** the OD-4 phone-gate on `orders` & `seller_profiles` is RESTRICTIVE-only with no PERMISSIVE ownership INSERT policy. Because a RESTRICTIVE policy can only subtract from what permissive policies allow, ALL authenticated inserts to these two tables are currently denied — phone or not. Phase 07 (checkout/orders) and Phase 04 (become-seller/seller_profiles) MUST add the permissive ownership INSERT policy so the phone-gate has something to restrict. `payouts` already has both (`payouts_insert` permissive + `payouts_phone_gate` restrictive) and is the working model; the harness proves the positive path there.
- **T08 finding — phone-gate denial not isolated on orders:** assertion 4 proves the positive path on `payouts` and a negative on `orders`, but the orders negative passes via default-deny (no permissive INSERT), not the gate itself. Optional hardening: add a payouts negative — service-role-seed a phone-NULL store owner, assert their `payouts` INSERT is rejected — to isolate the gate's denying effect from default-deny. Not blocking; track for the Phase 07 / 04 gate verification.
- **T08 finding — append-only tables are undeletable via the Data API:** `order_status_history` & `moderation_logs` carry `DO INSTEAD NOTHING` UPDATE/DELETE RULES, so rows inserted through PostgREST can never be torn down by the harness. Assertion 5 is therefore opt-in (`RLS_TEST_APPEND_ONLY=1`); by default it is recorded as a finding (enforcement is structurally guaranteed by the rules + absence of non-admin UPDATE/DELETE policies).
